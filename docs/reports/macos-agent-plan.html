macOS agent rebuild plan

Based on: final-osworld (18/107), the calc-v19 smoke run after the prompt fix, the code in macos_tools.py, the macos-osascript server, agent_library.py and scripts/macarena

This plan answers the five questions you asked, using the failures as evidence. The short version: keep the architecture and rebuild the layer the model talks to. Today the model has to write exact AppleScript paths and click one control at a time. It should instead get observation tools that return a whole screen, table or dialog in one call, and app adapters that act on the live document. It also matters what we can't conclude yet: the run used a small local model with thinking turned off, so part of the gap may be the model rather than the harness.

Answers

Partly
Refactor the harness and skills?

Yes for the layer the model sees, no for the plumbing. One toolkit run in the VM through the bridge, and one prompt built from shared sections, is the right design; keep it. Change four things. The harness, not the prompt, should give the agent its starting state. App knowledge should load on demand as skills, for both agents (the benchmark agent currently loads none). Rules about budget, retries and finishing should be enforced by middleware, not written as prose. And the 3,200-line toolkit file should be split into modules.

Not as-is
A Playwright tool for browsers?

We need what Playwright offers (a page snapshot with references, then fill, select and wait), but not the Playwright MCP the app already has. That MCP launches its own Chromium, while the checkers, and the user's logins, live in the Chrome that's already open. So build a set of browser_* tools in the macOS toolkit that attach to that Chrome. They'd use the DevTools protocol (CDP) in the benchmark, and an extension or Apple Events bridge for the user's own Chrome in the app.

Yes
More custom tools, at both levels?

Yes. The small tools are general: choose a menu item by its path, search menus, read a dialog, fill a dialog, read a table, and one "what's on screen" call. The large tools are per-app adapters that act on the live document: LibreOffice through its UNO scripting interface, GIMP through its Script-Fu server, System Settings through pane links and defaults. Don't build per-task tools.

Yes
Fewer turns, e.g. a table or cell reader?

Yes, and this is cheap. One task spent 93 of its 100 tool calls reading cells one at a time. Add a range reader, batched value reads, reads of whole dialogs, and results that report only what changed instead of an 8,000-character dump of every control. Most of the turn savings come from the menu and dialog tools, not just the table reader.

Caveat
Reviewed against the failures?

Each workstream below names the failed tasks it targets. The caveat is attribution. The model was Qwen3.6-35B-A3B in 8-bit with thinking turned off. Until the same harness has been run with a frontier model, we can't say which failures the tools would fix and which the model would. That run is step 0.

What the evidence says, and what it doesn't

The prompt fix already happened, and it wasn't enough.

After the run, "Look first: take one full-screen read before choosing an app" was added to the benchmark prompt. In the calc-v19 smoke run, every trajectory started with read_screen and worked in LibreOffice, so the app-choice problem went away. The score was still 1 of 6. The agents then ran out of turns on the next problem: "LibreOffice's menu bar not being accessible through the available tools", a chart wizard it couldn't drive, a Tips "Allow" dialog, and the info banner. Fixing app choice exposes the interaction layer as the next limit.

Product and benchmark are different goals.

Some fixes only matter for the benchmark: the UTM reset crash, the pkill chrome and GIMP config-flush checker problems, and the 30-turn budget. Fix those in scripts/macarena and nowhere else. Everything in the workstreams below is chosen because it also helps a real user's Mac. If a change only raises the score, it doesn't go into the toolkit.

Target architecture

The same layers run in the app and in the benchmark. Only the outer frame differs: the benchmark adds a budget, vm_done/vm_fail, no user, and the guard. Everything in the toolkit keeps reaching the VM through the existing remote path (backend/macarena_native.py), so any new dependency must run inside the guest bundle.

1. Harness and skills

Starting state comes from the harness, not the prompt

Before the model's first turn, middleware calls observe() and adds it to the task message. It lists the frontmost app and its real process name, window titles, the open document's path, the focused element, any open sheet or dialog, and running regular apps. In the app, the same block describes what the user is looking at. This makes "look first" a fact the agent starts with instead of an instruction it may ignore. It targets the 30 wrong-app failures.

App cards are skills, available to both agents

The app agent loads the macos-desktop and macos-applescript skills; the benchmark agent loads none, because skills arrive as files and it has no file tools. Add an app_guide(app) tool that returns the card's text. Middleware loads the frontmost app's card automatically. A card holds facts about the app, not task answers:

  • Identity: bundle ID, process name (soffice for LibreOffice), how to tell its windows apart.
  • Route: its scripting interface (UNO, Script-Fu, Chrome's AppleScript dictionary, or none), and when to use the UI instead.
  • Menu map and shortcuts for common operations (Insert ▸ Chart…, Format ▸ Cells…, View ▸ Zoom), and how to jump to a cell (the Name Box).
  • Save rules: LibreOffice's "Keep current format" dialog for .xlsx, GIMP's difference between Export and Save, and that the source file must never be overwritten.
  • Features it lacks: GIMP 3.2 has no CMYK mode, no video editing, no SVG export. Write these from documentation, not from the OSWorld list of infeasible tasks, and test them on tasks they weren't written from (see section 6).

Rules move from prose into middleware

  • Same-goal retry counter: two failures of one approach on one goal, then the next result tells the agent to switch approach and names the alternatives from the app card. This extends the existing failure notice.
  • Budget warning: when 3 turns are left, the result says so and tells the agent to call vm_fail now if the task is infeasible. A late vm_fail is currently rejected, and that cost 0d8b7de3.
  • Feasibility checkpoint: the first write_todos must contain a feasibility verdict with the feature it depends on. If the agent's chosen approach doesn't use the app the task names (Pillow instead of GIMP), the next result asks it to re-check feasibility.
  • Finish gate: vm_done, or ending a turn in the app, requires that the most recent observation was taken after the last action that changed state.
  • Malformed-call recovery: if a reply contains <tool_call> or <function= as text, or the agent finishes on its first turn with no tool call, ask it to answer again with a real tool call. This is cheap and affects every local-model run.
  • Interrupt handling: every observation names any blocking dialog or banner (Tips "Allow", LibreOffice's info banner, "Keep current format") and the button to dismiss it.

Split the code

Split src/tools/navigation/computer/macos_tools.py (3,197 lines) into modules: ax/ (primitives and walking), observe/, act/, browser/ and apps/{libreoffice,gimp,chrome,settings}. Each tool declares its action-policy category and step cost where it's defined, so scripts/macarena/native_tools.py no longer keeps its own copies of those sets. Also fix the defects found here: list_apps() with no query lists running apps; process name aliasing; click_text reaching the menu bar.

2. Browser

Why not add the existing Playwright MCP to the desktop agent? _build_playwright_command starts its own bundled Chromium with its own profile. The OSWorld checkers read the active tab of the Chrome that setup started with --remote-debugging-port=1337, and a user's logins and open tabs are in their own Chrome. Neither would be in the Playwright browser. The MCP also needs Node, which the guest bundle doesn't have. Keep browser-agent for research and scraping, where a clean browser is fine.

What to build: a set of browser_* tools in the toolkit with Playwright MCP's interface, run against the browser that's already open. Some of this already exists: read_app_dom and click_app_dom talk CDP over aiohttp, and they ran in the benchmark (2ae9ba84 44ee5668).

Backends:

  • CDP, when Chrome has a debugging port. This is always true in the benchmark, and true in the app when Otto started Chrome with a separate profile. It runs in the guest over aiohttp, so no Node is needed.
  • The user's everyday Chrome. My understanding is that recent Chrome versions ignore --remote-debugging-port on the default profile; this needs checking. If so, there are two options: a small Otto extension that relays CDP commands (Playwright MCP's extension mode works this way), or Chrome's AppleScript execute javascript, which needs the user to turn on "Allow JavaScript from Apple Events". If neither is available, fall back to today's accessibility path.
  • Safari, later: AppleScript do JavaScript with the same opt-in setting.

Expected effect: the 5 hard web flows (44ee5668 47543840 82279c77 7f52cab9 f0b971a1) and the Chrome settings tasks. The 10 Chrome wrong-app failures are fixed by the starting-state work, not by this. This is the third-largest lever, not the first.

Is the UNO adapter fair in the benchmark? The native track already allows AppleScript, which is how the agent scripts Numbers. UNO is LibreOffice's equivalent scripting interface, and using it fits Otto's "script when the app supports it" approach. Report it openly as part of the native track's tool set. Don't present those scores as GUI-only results.

Don't build: per-task tools ("insert growth chart"), tools that click at pixel positions, or tools that edit a document's file on disk while the app has it open.

4. Fewer turns

  • Bulk reads: read_table, get_control_values and read_dialog. One call per screen of data.
  • Report what changed: after an action, return what changed (a new dialog, a value that changed, a new window), with the full controls list only when asked. Today's 8,000-character dump after every action fills a small model's context and buries the signal.
  • Accept intent: menu_select, fill_dialog and the adapter helpers do in one call what takes 5–10 today.
  • Batch more: let batch_actions mix adapter calls with UI actions, and stop at the first step whose check fails.
  • Fix the cheap waste: list_apps() with no query (one call instead of 5–17), no calls after the run is over (47 were rejected), and the starting state (saves 2–6 opening turns per task).
  • Measure it: add median turns per solved task and the share of turns spent on reads to report.py, so turn savings show up separately from score changes.

5. The model question

The benchmark ran mlx-community/Qwen3.6-35B-A3B-8bit through oMLX with thinking turned off. That model has about 3B active parameters. Several failures look like what a small model does: AppleScript syntax errors, tool calls written as text, poor feasibility judgments, and repeating calls that already failed. The plan is built so a small model can succeed: the tools take intent, return compact results, and leave little exact syntax to write. But the rebuild shouldn't be planned before we know where the limit is.

  • Baseline: run the same harness, with no tool changes, on a fixed 40-task slice using a frontier model (Claude Opus 5.5 or Sonnet 5.5), and again with Qwen with thinking on. If the frontier model reaches about 60% on unchanged tools, the work goes to model-side support. If it also stalls on LibreOffice menus, the tools are the limit, which is what I expect.
  • App only: consider a split where a stronger model plans and a local model executes the tool calls. Decide once the baseline shows where the turns go wrong.

6. Measurement rules

  • Dev and held-out sets: tune on OSWorld chrome, calc and gimp. Hold out OSWorld writer, os, vs_code and thunderbird, all of macOSWorld, and MacArena's own tasks. Report both. A card or tool that helps the dev set but not the held-out set is overfitted.
  • No task answers in cards: before merging, check that no card or prompt mentions a task's specific file, value or URL. Write the lists of missing features from the app's documentation.
  • Regression set: the failed task IDs in this plan become a fixed regression suite, with each failure's main cause attached.
  • Fix the benchmark first: fix the reset health check, confirm the 3 suspected checker bugs, and rerun the 16 infra tasks before comparing anything.
  • Fixed protocol: keep one budget (30 turns) and one tool-call cap for comparisons. Report 60-turn results separately. More turns hide inefficiency rather than fix it.

menu_select, menu_search, read_dialog, fill_dialog, read_table, get_control_values, wait_until, and the toolkit split into modules.

App adapters (2 weeks)

The LibreOffice UNO adapter first (it covers the most tasks), then GIMP Script-Fu, then System Settings, plus app cards for each.

Done when: calc on the dev set goes from 3/35 to ≥ 15/35, and writer (held out) improves without being tuned on.

4

Browser (1–2 weeks)

browser_* over CDP in the guest, then the app backend for the user's own Chrome (extension or Apple Events), once it's confirmed which one Chrome allows.

Done when: chrome goes from 12/32 to ≥ 20/32, and the tools work against a real user's logged-in Chrome in the app.

5

Feasibility and finishing (ongoing)

Feasibility checkpoint and finish gate, with lists of missing features checked against the held-out infeasible tasks.

Done when: infeasible tasks pass at ≥ 60% (3/14 now), feasible tasks are wrongly failed in ≤ 5% of cases, and the same holds on held-out tasks.

Risks and things I'm not sure of

  • Starting UNO on a running instance: I haven't confirmed that a running LibreOffice starts accepting connections when sent --accept. If it doesn't, Otto must start LibreOffice with it. In the benchmark, that means relaunching before the agent starts, which changes the task's starting state.
  • GIMP 3.2: I haven't confirmed the Script-Fu server and its procedure names in 3.2. If live scripting isn't available, GIMP stays UI-bound and its gains come only from menu_select and fill_dialog.
  • Chrome debugging limits on the default profile need checking against the Chrome version users run. The extension route adds an install step and a review surface.
  • The targets are estimates. They come from failure counts that overlap, not from measurements. Phase 0 can change the order of the work.
  • Context size: app cards and starting-state blocks add tokens. With a 128K window and thinking on, measure that the prompt stays under about 15K tokens.
  • Safety in the app: uno_exec, gimp_eval and browser_eval are code execution. They go through the action policy with their own categories and are off by default for agents built by users.
